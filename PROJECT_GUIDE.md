# Task. — Project guide

This guide explains how the Task. website is put together, how information moves through it, and where to make common changes. It describes the implementation in this repository; it is not a separate backend or API specification.

## 1. What the application does

Task. is a browser-based task manager built with React and TypeScript. It has a dashboard, a searchable and filterable task list, a Kanban board, task detail pages, and settings.

There is no server, account system, or API. Tasks and the theme preference are saved in the current browser's `localStorage`. The data is not synchronized between browsers or devices.

## 2. Start, build, and test

Requirements: Node.js and npm.

```bash
npm install
npm run dev
```

Vite prints a local URL after the development server starts.

| Command              | Purpose                                                      |
| -------------------- | ------------------------------------------------------------ |
| `npm run dev`        | Start the local development server with Vite                 |
| `npm run build`      | Run TypeScript project checks and build the production files |
| `npm run preview`    | Serve the production build locally                           |
| `npm test`           | Run the Vitest tests once                                    |
| `npm run test:watch` | Run Vitest interactively while developing                    |

Before sharing a code change, run `npm run build` and `npm test`. The TypeScript app configuration is strict, including checks for unused variables and unchecked indexed access.

## 3. Technology and application startup

- **React 18** renders the interface from reusable components.
- **TypeScript** defines task data and component contracts.
- **React Router** selects pages and provides navigation, URL search parameters, and route parameters.
- **Vite** runs the development server and builds the app.
- **Vitest**, Testing Library, and jsdom run the unit and component tests.
- **lucide-react** provides icons.

The browser entry point is `index.html`, which contains the `root` element and loads `src/main.tsx`.

The startup sequence in `src/main.tsx` is:

1. Find the `#root` element and create a React root.
2. Render the app in `React.StrictMode`.
3. Add `BrowserRouter`, so links and URL changes select routes.
4. Add `TasksProvider`, so every page can access the shared task list.
5. Load the global stylesheet.

`src/App.tsx` declares the routes. `AppLayout` is the shared page shell: it provides the sidebar, header, page outlet, theme state, and a create-task dialog available from the header.

## 5. Routes and what each page does

Routes are defined in `src/App.tsx` and rendered inside the shared `AppLayout`.

| URL              | Page             | Main responsibilities                                                                           |
| ---------------- | ---------------- | ----------------------------------------------------------------------------------------------- |
| `/`              | `DashboardPage`  | Shows task totals, completion, active work, recent tasks, and a quick-add action                |
| `/tasks`         | `TasksPage`      | Displays tasks in a table; supports search, filters, sorting, create, edit, and delete          |
| `/tasks/:taskId` | `TaskDetailPage` | Looks up a task by its ID; shows details and allows editing, deletion, and status changes       |
| `/board`         | `KanbanPage`     | Groups tasks into Todo, In Progress, and Done columns; supports status changes and task editing |
| `/settings`      | `SettingsPage`   | Changes the theme and restores demo tasks or clears all tasks                                   |
| Any other URL    | `NotFoundPage`   | Shows a not-found message and a link to the dashboard                                           |

The sidebar navigation is in `src/components/layout/Sidebar.tsx`. The header in `src/components/layout/Header.tsx` chooses a title based on the current route and owns the global search input. The search shortcut is **Ctrl+K** on most platforms and **Command+K** on Mac.

### Search behavior

The header stores the search string in the URL query parameter `q`, for example `/tasks?q=design`. Typing in search from another page navigates to `/tasks`. The task list reads `q` from the URL and combines it with its status, priority, category, and sort controls. Those other controls are local to the mounted task-list page; they are not encoded in the URL.

## 6. Task data model

`src/types/task.ts` is the canonical place to define task-related types.

| Field         | Type           | Meaning                                                               |
| ------------- | -------------- | --------------------------------------------------------------------- |
| `id`          | `string`       | Unique task identifier                                                |
| `title`       | `string`       | Required task name                                                    |
| `description` | `string`       | Optional explanatory text, represented as an empty string when absent |
| `status`      | `TaskStatus`   | One of `Todo`, `In Progress`, or `Done`                               |
| `priority`    | `TaskPriority` | One of `Low`, `Medium`, `High`, or `Critical`                         |
| `dueDate`     | `string`       | Optional calendar date in `YYYY-MM-DD` format                         |
| `assignee`    | `string`       | Optional person's name                                                |
| `category`    | `string`       | Optional free-text category                                           |
| `createdAt`   | `string`       | Creation timestamp in ISO format                                      |
| `updatedAt`   | `string`       | Most recent edit timestamp in ISO format                              |

`TaskFormValues` contains the user-editable fields, excluding generated IDs and timestamps. `TaskFilters` describes all filtering and sorting inputs. `Theme` is the `light` or `dark` setting.

The status and priority arrays in `task.ts` are the source of truth for their TypeScript union types. Forms and status controls use those arrays to create their options.

## 7. Task state, actions, and persistence

`src/hooks/useTasks.tsx` implements a React context:

- `TasksProvider` loads the initial task list and makes it available to the application.
- `useTasks()` gives a component access to the list and task actions.
- The hook throws an error if called outside `TasksProvider`, which usually means the component is rendered outside the app's provider tree.

Task actions are:

| Action                     | Result                                                                   |
| -------------------------- | ------------------------------------------------------------------------ |
| `addTask(values)`          | Creates a UUID and timestamps, then adds a task to the start of the list |
| `updateTask(id, values)`   | Replaces editable fields and refreshes `updatedAt`                       |
| `deleteTask(id)`           | Removes the task with that ID                                            |
| `updateStatus(id, status)` | Changes status and refreshes `updatedAt`                                 |
| `resetTasks()`             | Replaces the list with a fresh set of sample tasks                       |
| `clearTasks()`             | Sets the list to an empty array                                          |

`src/utils/taskHelpers.ts` owns the storage key `orbit.tasks.v1`, sample data, and persisted-data validation. On startup:

1. If the key is absent, the app starts with demo tasks.
2. If saved JSON is valid and every item has the expected task shape, the app restores it.
3. If the saved JSON cannot be parsed, storage access fails, or the task shape is invalid, an error is logged and the app uses demo tasks.
4. Whenever task state changes, the provider serializes it back to local storage.

Theme preference is stored separately under `orbit.theme.v1` by `AppLayout`. Changing theme sets `data-theme` on the document root; CSS variables respond to that attribute.

**Data warning:** clearing browser/site data removes these saved tasks and theme settings. The app has no remote backup. If you change the task model, update the `isTask` check and consider how existing saved data should be migrated; otherwise old records with a different shape will be treated as invalid.

## 8. Shared helpers and derived values

`src/utils/taskHelpers.ts` contains logic that should stay independent of page markup:

- `defaultTaskFormValues()` supplies initial form field values.
- `emptyTaskFilters()` supplies the default filter state.
- `filterAndSortTasks(tasks, filters)` matches search against title and description, applies status/priority/category filters, and sorts by creation date or due date.
- `getTaskStats(tasks)` calculates total, completed, in-progress, Todo, overdue, and completion percentage values for the dashboard.
- `isValidDueDate(value)` permits an empty optional date and validates real calendar dates in `YYYY-MM-DD` form.
- `createDemoTasks()` creates the sample list with dates relative to the current day.
- `readStoredTasks(storage)` reads and validates saved data.

Keep derived dashboard counts in `getTaskStats` rather than duplicating the calculations in UI components. The dashboard uses `filterAndSortTasks` to show the five most recently created tasks.

## 9. Forms and task actions

`src/components/tasks/TaskFormDialog.tsx` is the shared create/edit form. Pages provide:

- `title`: dialog heading;
- `initialValues`: initial field data;
- `onClose`: how to close the dialog;
- `onSubmit`: what to do with valid form values.

The form handles its own field state and validation. It trims the title, description, assignee, and category before saving; requires a non-empty title of at most 100 characters; and validates the optional due date. It also blocks duplicate submissions while saving.

The same form is reused in the dashboard, task list, Kanban board, task detail page, and app header. This keeps task entry behavior consistent. If you add or change a task field, update the shared form and the callers' default values as appropriate.

`TaskTable` is the shared list view. `TaskStatusBadge` and `TaskPriorityBadge` provide consistent status/priority labels across views. `formatDueDate` is also exported from `TaskTable` and reused by other pages.

## 10. Page details

### Dashboard

`src/pages/DashboardPage.tsx` reads tasks from `useTasks`, derives statistics, and renders reusable `StatCard` components. It also displays recent tasks and opens the shared dialog to add or edit a task. The dashboard's stat values are calculated from the current in-memory list, which is persisted by the provider.

### All tasks

`src/pages/TasksPage.tsx` keeps non-search filters in local React state and reads search text from `q`. It derives category options from the current tasks, then passes the filtered and sorted list into `TaskTable`. Delete is protected by the browser confirmation dialog. The page owns create/edit dialog state.

### Task detail

`src/pages/TaskDetailPage.tsx` reads `taskId` from the route and finds the matching task in shared state. A missing or deleted ID shows an inline message. A confirmed delete returns the user to `/tasks`.

### Kanban board

`src/pages/KanbanPage.tsx` defines its columns from the available statuses and filters the shared task list for each one. The status dropdown calls `updateStatus`, which immediately updates all views and local storage. Adding a task from a column sets that column's status as the form default.

### Settings

`src/pages/SettingsPage.tsx` receives theme state from `AppLayout` through the router outlet context, and task actions from `useTasks`. Both replacing tasks with demo data and clearing tasks require confirmation.

## 11. Styling and responsive behavior

`src/styles/variables.css` defines the primary design tokens, including surfaces, borders, text, accent colors, and shadows. The `:root[data-theme="dark"]` selector overrides the tokens for dark mode. Prefer editing or adding variables here rather than hard-coding a color across multiple components.

`src/styles/global.css` contains global resets, layout, component classes, and responsive media queries. Class names are intentionally shared across pages (for example `.button`, `.panel`, `.badge`, and `.form-control`).

Responsive behavior is implemented with CSS breakpoints:

- At widths up to `820px`, the sidebar becomes a horizontal top navigation and the Kanban columns scroll horizontally.
- At widths up to `620px`, navigation moves to the bottom of the screen, the header and forms become more compact, and controls get larger touch targets.
- At widths up to `380px`, dashboard cards and spacing are further adjusted.
- Reduced-motion preferences are respected near the end of the stylesheet.

When changing a component's markup, check both its desktop and mobile CSS. The project currently uses a single global stylesheet rather than CSS modules or a component styling library.

## 12. Tests

Tests use Vitest with the jsdom browser environment. `src/test/setup.ts` loads Testing Library's Jest DOM matchers.

- `src/utils/taskHelpers.test.ts` checks filtering, sort order, statistics, date validation, and storage restoration.
- `src/hooks/useTasks.test.tsx` checks adding, updating, deleting, persistence, and handling storage write errors.

When changing a helper, update or add a focused unit test in its matching test file. When changing shared state or persistence, test observable behavior through the provider. For UI behavior, Testing Library can render a page/component and interact with it as a user would.

## 13. Common changes: where to start

### Change a label or page text

Find the page or component that renders the text, usually under `src/pages` or `src/components`. Keep actual screen-reader labels (`aria-label`, `.sr-only`) in sync with visible control behavior.

### Add a new task field

1. Add the property to `Task` and `TaskFormValues` in `src/types/task.ts`.
2. Add its default in `defaultTaskFormValues()` in `src/utils/taskHelpers.ts`.
3. Add a form control and update logic in `TaskFormDialog.tsx`.
4. Add the field to the persisted-task shape check (`isTask`) in `taskHelpers.ts`.
5. Decide how to handle existing saved tasks, which do not contain the new property. Add a migration or intentionally handle old records; otherwise they fail validation and demo tasks are loaded.
6. Display it in whichever views need it (table, board, detail, dashboard).
7. Update the tests for defaults, form behavior, and storage validation as relevant.
8. Run `npm run build` and `npm test`.

### Add a status or priority

Update the relevant constant array in `src/types/task.ts` first. Then inspect all status/priority-dependent surfaces: form choices, filters, badges and their CSS classes, Kanban columns, dashboard statistics, status labels, and tests. Status values drive the board columns, so adding a status may require deciding whether the board should display another column.

### Add a page

Create a page component under `src/pages`, register a route in `src/App.tsx`, and add a navigation link in `src/components/layout/Sidebar.tsx` if the page should be in the main navigation. Update the route title map in `Header.tsx` if the header should have a custom title. Add responsive styles and tests where appropriate.

### Change task search or sorting

Update the algorithm in `filterAndSortTasks()` in `src/utils/taskHelpers.ts`; this function is shared by the task list and dashboard. Add tests to `src/utils/taskHelpers.test.ts`. The header's URL handling is in `src/components/layout/Header.tsx`, while task-list filter controls are in `src/pages/TasksPage.tsx`.

### Change theme colors

Edit the CSS variables in `src/styles/variables.css`. If you add a token, provide both light and dark values when the visual should work in both themes.

### Change what is stored in the browser

Task persistence is in `src/hooks/useTasks.tsx` and `src/utils/taskHelpers.ts`; theme persistence is in `src/components/layout/AppLayout.tsx`. Keep storage parsing guarded and test invalid data and storage failures. Changing a storage key or data shape can affect data already saved in users' browsers.

## 14. Useful implementation conventions

- Keep task state changes in the `TasksProvider`; pages should call its actions rather than maintaining separate copies of tasks.
- Keep shared task shapes and allowed values in `src/types/task.ts`.
- Keep reusable calculations and validation in `src/utils/taskHelpers.ts`.
- Reuse shared UI such as `TaskFormDialog`, `TaskTable`, and badges rather than implementing a one-off version on one page.
- Use the CSS variables for theme-aware colors.
- Maintain labels and accessible names when changing controls.
- Add tests for behavior, not just markup, when changing shared logic.

## 15. Current limitations

- Tasks and theme are stored only in this browser profile and origin.
- There is no login, server, multi-user collaboration, cloud synchronization, or automatic backup.
- Categories and assignees are free-text fields rather than managed entities.
- The Kanban board changes status with a select control; it does not implement drag-and-drop.
- Task search matches title and description, not category, assignee, or status.
- Invalid stored task data falls back to demo tasks; there is not currently a user-facing import or recovery flow.
